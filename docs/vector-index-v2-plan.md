# 向量索引 V2 方案

## 背景

当前项目的剧情检索能力已经具备基础可用性：

- 以剧情大纲场景为最小分段单位
- 将标题、简介、场景描述、镜头解读等文本拼接为单一 `searchable_text`
- 按项目生成和存储向量
- 基于 `sqlite-vec` 做项目内语义检索

这套方案对当前“根据剧情找到对应画面”的核心场景是成立的，但随着镜头解读、字幕、解说价值点等信息持续增加，现有结构已经开始暴露几个问题：

- 不同来源的文本被混合到一个字段中，无法做来源区分和权重控制
- 所有检索内容都被压缩成一种 `scene` 粒度，不利于细粒度召回
- 同一个素材挂到多个项目时，向量会按项目重复存储
- 难以解释“为什么命中”
- 后续做重排、混合检索、字段筛选时约束较大

因此需要规划 V2 方案，为后续内容检索能力做结构化升级。

---

## 当前实现概览

### 当前分段单位

当前 segment 以剧情大纲中的场景为单位，每个场景形成一条检索记录。

### 当前文本组织方式

当前 `searchable_text` 由以下内容直接拼接得到：

- 素材标题
- 素材简介
- 场景标题
- 场景描述
- 镜头解读内容

### 当前存储层

当前有两层数据：

1. 普通表 `asset_outline_segment`
   - 存场景级元数据
   - 存 `searchable_text`
   - 存 embedding 状态和可选 embedding JSON

2. `sqlite-vec` 虚表
   - 表名按向量维度拆分
   - 行里直接带 `project_id`
   - 同一个素材在多个项目里会生成多份向量记录

### 当前查询路径

查询时按以下路径进行：

1. 对 query 生成 embedding
2. 在当前项目对应的向量分区中检索
3. 通过 `segment_id` 回表拿 segment 元数据
4. 返回剧情片段结果

### 当前优点

- 结构简单，易于实现
- 项目级隔离明确
- 与当前业务需求高度贴合
- 对远端 embedding 和本地 embedding 都兼容

---

## 当前问题

### 1. 文本来源混合，无法控制权重

例如：

- 场景描述是剧情摘要
- 镜头解读是视觉语义
- 字幕是对白文本

这些信息来源完全不同，但当前会被拼成一条文本。这样虽然简单，但会导致：

- 某一类文本噪声过大时影响整体 embedding
- 无法按字段调整权重
- 无法区分“视觉命中”还是“对白命中”

### 2. 粒度单一

当前只有“场景级”一种 segment 粒度。后续如果需要支持：

- 搜对白
- 搜镜头语言
- 搜人物动作
- 搜解说价值点

都会被迫塞进同一个场景向量里，召回效果和可解释性都会受限。

### 3. 项目级重复存储

当前向量表按 `project_id` 存储。同一素材如果被多个项目复用，会重复写多份向量。

问题包括：

- 存储重复
- 索引重建成本增加
- 后续跨项目复用能力较弱

### 4. 难以做混合检索

如果以后要做以下能力，当前结构会比较吃力：

- 字幕精确匹配 + 语义召回
- 不同字段不同权重
- 特定类型 segment 的筛选
- 结果解释和调试

---

## V2 设计目标

V2 方案希望解决以下问题：

1. 将不同语义来源结构化，而不是全部混拼
2. 支持多种 segment 类型
3. 尽量减少向量重复存储
4. 保持对现有业务的兼容
5. 保持实现复杂度可控，允许分阶段上线

---

## 核心思路

V2 不再把“可检索内容”视为单一的剧情场景文本，而是视为一组结构化的检索段。

每条检索段都具备：

- 所属素材
- 所属场景
- 段类型
- 来源文本
- 归一化文本
- 向量
- 时间范围

### 建议的 segment 类型

- `scene_summary`
  - 来自场景标题 + 场景描述
  - 用于剧情级召回

- `shot_analysis`
  - 来自镜头解读
  - 用于视觉内容召回

- `subtitle_window`
  - 来自场景时间范围内的字幕切片
  - 用于对白/台词召回

- `commentary_hook`
  - 来自镜头解读里的 `commentaryHooks`
  - 用于解说点检索

后续可扩展：

- `character_action`
- `screen_text`
- `music_or_sound`

---

## 建议的数据结构

### 1. 检索段元数据表

建议新增一张统一的 segment 表，例如：

`content_segment`

字段建议：

- `id`
- `asset_id`
- `scene_id`
- `segment_type`
- `title_text`
- `summary_text`
- `subtitle_text`
- `shot_text`
- `hook_text`
- `searchable_text`
- `start_seconds`
- `end_seconds`
- `timestamp_text`
- `source_version`
- `updated_at`

说明：

- `searchable_text` 仍然保留，但它变成派生字段，而不是唯一真相
- 真正的真相是结构化字段

### 2. 向量表

建议将向量主存储从“项目级副本”改为“素材级主索引”。

例如新增统一向量记录：

`content_segment_embedding`

字段建议：

- `segment_id`
- `asset_id`
- `embedding_model`
- `embedding_dimension`
- `embedding_status`
- `embedding_error`
- `updated_at`

如果继续使用 `sqlite-vec`，则虚表建议按维度存储，但不再把 `project_id` 作为主分区字段，而是只存：

- `asset_id`
- `segment_id`
- `embedding_model`
- `segment_type`
- `start_seconds`
- `embedding`

### 3. 项目关联层

项目级过滤不再靠重复存储向量，而是靠映射关系：

- `project_asset`
- `asset_id -> segment_id`

查询时：

1. 在素材级向量索引中召回候选
2. 再通过 `project_asset` 过滤出属于当前项目的素材

如果 `sqlite-vec` 在这种 join 模式下性能不理想，再考虑保留项目级缓存层。

## 检索流程建议

### 方案 A：基础版

1. 根据 query 生成 embedding
2. 在素材级向量表中检索 top-k candidates
3. 通过 `project_asset` 过滤出当前项目可见素材
4. 回表拿 `content_segment`
5. 返回结果

优点：

- 存储不重复
- 结构更清晰

缺点：

- 查询路径比当前多一步过滤

### 方案 B：混合召回版

1. 关键词召回 `subtitle_window` / `scene_summary`
2. 向量召回 `scene_summary` / `shot_analysis`
3. 合并候选
4. 如果允许，使用 LLM 做重排

优点：

- 对中文场景更稳
- 对字幕精确命中更好
- 对视觉语义召回更强

这是更推荐的中期方向。

---

## 文本构造建议

V2 中不建议把所有文本一股脑拼起来生成同一个 embedding。

### 推荐做法

按 segment 类型分别构造文本：

#### `scene_summary`

- 场景标题
- 场景描述
- 素材标题
- 素材简介

#### `shot_analysis`

- 镜头解读 summary
- action
- expressionAndGaze
- cinematography
- atmosphere

#### `subtitle_window`

- 当前场景时间范围内字幕文本

#### `commentary_hook`

- commentaryHooks

这样做的好处：

- 每种向量语义更纯
- 后续可按 segment type 做权重
- 调试时更容易看出问题

---

## 为什么不建议继续只用单一场景向量

单一场景向量短期可以工作，但会逐步遇到下面的问题：

- 镜头解读和剧情摘要互相污染
- 字幕中高频对白掩盖视觉信息
- 一条 query 其实只想找“镜头语言”，却被剧情描述主导
- 很难解释命中原因

所以不建议继续无限扩展单一 `searchable_text`。

---

## 迁移策略

### 阶段 1：低风险增强

目标：先把结构演进埋进去，但不推翻现有链路。

做法：

1. 保留现有 `asset_outline_segment`
2. 为它新增 `segment_type`
3. 开始把镜头解读、字幕切片拆成额外 segment
4. 查询时仍然沿用当前逻辑
5. 让搜索结果支持展示 segment 类型

这一阶段成本最低，适合快速验证效果。

### 阶段 2：素材级主索引

目标：减少项目级重复向量。

做法：

1. 新建素材级向量表
2. 新查询链路先查素材级索引
3. 通过 `project_asset` 过滤项目可见范围
4. 保留旧项目级向量作为兼容层

### 阶段 3：混合召回

目标：提升召回质量和解释性。

做法：

1. 不同 segment type 分别召回
2. 融合排序
3. 需要时接 LLM 重排

---

## 推荐落地顺序

建议按下面的顺序实施，而不是一次性重写：

1. 为 segment 增加 `segment_type`
2. 将场景摘要、镜头解读、字幕切片拆成多条 segment
3. 查询结果里返回 `segment_type`
4. 验证实际召回效果
5. 再考虑是否切换到素材级主索引

这是最稳妥的路径。

---

## 建议的 V2 最小可交付版本

如果只做一个最小可落地版本，我建议：

### 保留

- 现有场景级索引能力
- 现有项目搜索接口
- 现有 embedding 配置方式

### 新增

- `segment_type`
- 多类型 segment 构造
- 镜头解读和字幕切片拆段
- 检索时按 segment type 返回结果

### 暂不做

- 全量素材级向量主索引切换
- 复杂权重融合
- 多路召回重排

这样可以先低成本验证“多类型 segment”是否显著提升检索质量。

---

## 结论

当前结构在项目当前阶段是可用的，但已经不适合继续无限追加文本来源。

推荐方向不是彻底推翻，而是演进到：

- 多类型 segment
- 结构化文本字段
- 逐步从项目级重复向量过渡到素材级主索引

优先级建议：

1. 先做 segment 类型化
2. 再做多来源拆段
3. 最后评估是否切到素材级向量主索引

这会比一次性重做更稳，也更适合当前项目节奏。
